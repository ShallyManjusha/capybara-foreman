01

Scope and stance

AI-SDLC Foreman watches a Jira board. When a ticket appears it reads the ticket and the code, establishes what is actually wrong, and posts an analysis and a change plan back on the ticket — then stops and waits for a person. On approval it writes the code, opens a pull request, triggers the non-prod deployment, writes unit tests for the acceptance criteria that were agreed, runs them, and posts the evidence — then stops again. On sign-off it closes the ticket and raises the production-deployment ticket for a human to schedule.

Nobody prompts it. It runs from cron.

What is automated, and what is not

Coding agents are good at the middle of this and bad at the ends. The middle — read the code, find the defect, write the fix, write the tests — is where they earn their keep. The ends are where they go wrong: deciding which work to do, deciding whether a change is good enough to ship, and deciding when something needs a person.

Most agent demonstrations automate the middle and hand-wave the ends. That is why they demonstrate well and deploy badly. Foreman is the ends: a state machine with two human gates wrapped around Bob Shell. Every interesting decision belongs to a named person and is recorded on the ticket. What is automated is everything between those decisions, which turns out to be most of the clock time.

The agent proposes. The harness disposes. A human decides. Everything in this document is an elaboration of that sentence.

Deliberately out of scope

  • Production deployment. Foreman sets a fixVersion and raises a deployment ticket. Everything upstream is reversible in minutes; a production release is not, and a comment on a Jira ticket is not informed consent for one on a team's behalf.
  • Merging, by default. FOREMAN_AUTO_MERGE exists and defaults to false. Most teams want the merge button to stay human even when everything else does not.
  • Segregation of duty. Foreman records who approved and verifies their identity. Whether one person may both raise and approve is the client's change-management policy, expressed in FOREMAN_APPROVERS.
  • Deciding what to work on. The intake JQL is the outer boundary, and a human writes it.
02

System context

Four systems, and Foreman is the smallest of them. It holds no queue of its own, no workflow engine and no scheduler: cron starts it, the board tells it what to do, and it advances one ticket by one state before exiting.

Why one state per run

advance() performs exactly one transition per ticket per run, even when the next stage could start immediately. Every run is bounded in time and cost, so cron scheduling is predictable. The board stays legible while work moves — someone watching sees each step. An operator can stop the pipeline between any two stages by stopping the cron, with no in-flight state to reconcile. And a bug in one stage cannot cascade through five before anyone notices.

The cost is latency: a ticket needs six runs to reach done. At a ten-minute cron that is an hour of wall clock against days of queue time, and the two human gates dominate anyway.

03

Tiers and trust boundaries

A Jira ticket can be opened by a customer, a contractor, or a web form. Its text reaches a model that, four stages later, commits code. That is a path from a stranger typed something to code ran, and the tier separation is what makes that path safe to have.

The child environment is built by allowlist in adapter._child_env() — PATH, HOME, the Bob key and a handful of locale variables — not by unsetting known-bad names. An allowlist fails closed the moment someone adds a variable; a denylist fails open.

TierToolsCredentialsWorkspaceOutput
AnalysisreadBOB_API_KEYread-only clone, remote strippedone JSON envelope
Buildread command edit(fileRegex)BOB_API_KEYdisposable worktree, no remotefiles on disk
Control—Jira, git read, git writethe hostcomments, labels, branches, PRs

One consequence is worth stating plainly: even if the build stage's shell were fully compromised, there is no configured git remote in its worktree. Pushing requires the control tier to add one, push, and remove it again — which it does only after the diff has passed inspection.

04

The state machine

One ticket is in exactly one state. Each state either has a stage that Foreman runs, or it is a gate where Foreman stops and waits for a person. Nothing else moves a ticket.

The canonical definition lives in machine.py, in Python, not in the YAML. Policy tunes which Jira status each state mirrors onto; it cannot add a transition, remove a gate, or make a stage skip its guard. A configuration file that can delete a human approval gate is not a configuration file, it is a vulnerability.

Every legal move is one dictionary. Exhaustiveness is the point: a reader can audit the full set of ways a ticket can reach done by reading fifteen lines, and a unit test asserts that no gate can be bypassed.

// machine.py — the complete transition set
TRANSITIONS = {
    intake:              ["analyzed", "needs-info", "failed"],
    "analyzed":          ["awaiting-approval", "needs-info", "failed"],
    "awaiting-approval": ["approved", "revising", "rejected", "stalled", "failed"],
    "revising":          ["awaiting-approval", "needs-info", "failed"],
    "approved":          ["committed", "failed"],
    "committed":         ["deployed", "failed"],
    "deployed":          ["awaiting-signoff", "failed"],
    "awaiting-signoff":  ["closing", "reworking", "rejected", "stalled", "failed"],
    "reworking":         ["committed", "failed"],
    "closing":           ["done", "failed"],
    "done":              [],
    "rejected":          [],
    // recovery: back to the top, never resumed mid-flight —
    // the premises Foreman stopped on may no longer hold
    "needs-info":        [intake, "rejected"],
    "failed":            [intake, "rejected"],
    "stalled":           ["approved", "revising", "rejected", intake],
}

Mirroring onto the board's own workflow

Foreman's state lives in a label and an issue property, so it runs on a stock board with no custom workflow, no custom fields and no administrator rights. The optional status_map in foreman.yaml mirrors each state onto a Jira status where a matching one exists, and is skipped in silence where it does not. Requiring a bespoke workflow would make the system undeployable on most real projects; failing loudly when a status name does not match would make a workflow edit an outage.

05

The human gates

This is the most security-sensitive part of the system, and the reason is worth stating plainly. Downstream of an approval, an agent writes code and commits it. Upstream of it, anyone with a Jira licence can leave a comment. If "approved" means "someone typed the word approved", then the authorisation boundary for changing your source code is the same as the authorisation boundary for adding a thumbs-up to a ticket.

A reviewer replies on the ticket with one of three commands. Four independent checks must all pass before a comment counts as a decision.

CheckRejectsThe failure it prevents
Shapethe command is not the first text of the comment"I don't think we should /foreman approve yet" reading as an approval
Identityauthor not in FOREMAN_APPROVERSanyone with a Jira licence authorising a code change
Recencycomment predates gate_openeda stale approval silently authorising a later, different revision
Not usbody carries a Foreman markerthe rendered plan — which quotes the command, because it must tell the reviewer what to type — approving itself

An empty allowlist authorises nobody, never everybody. Every ticket stalls at the first gate and doctor reports it as a problem. The alternative default turns a misconfiguration into an open door.

Identifying Foreman's own comments

Filter 4 matches on the invisible marker every rendered comment carries, not on "the author is the account Foreman authenticates as". That version is both too strict and too weak. Too strict because a small team may run Foreman under an account a human also uses, and every approval would be silently discarded — a failure with no error anywhere. Too weak because it says nothing about a Foreman comment posted under some other identity. Matching on the marker asks the question actually meant: did Foreman write this?

Running Foreman under its own service account remains the right deployment, for a reason this check cannot help with: when the bot and the approver share an account, the ticket history cannot tell you who approved. doctor warns about it.

Timeouts

A gate that has waited longer than FOREMAN_APPROVAL_TIMEOUT_HOURS moves the ticket to stalled and reports it in the run summary. It is never auto-approved. There is no configuration value that causes a gate to pass without a decision, and that is deliberate — the absence of such a value is a property of the system, not an oversight.

06

Agent harness

Every Bob Shell invocation detail lives in adapter.py and nowhere else, so a Bob upgrade is a change to one file rather than to the pipeline. That file currently spans two incompatible CLI generations.

Bob Shell changed shape at 2.0: the headless entrypoint moved from top-level flags to a run subcommand, several flags were renamed, and --allowed-tools disappeared entirely — tool restriction moved into the mode definition's groups. The dialect is detected from --help, not configured. A fleet runs mixed versions for months during a rollout, and a harness that works only on the version its author had installed is a harness that fails on the first machine that is not theirs.

Tool access travels with the mode

In 2.x the analysis modes declare groups: [read]; the build mode declares [read, command, [edit, {fileRegex}]]. A restriction that travels with the mode cannot be forgotten by a caller, which is a better place for it than a flag at every call site. The fileRegex tuple form is a native per-mode path allowlist, and Foreman uses it — then re-checks the resulting diff anyway, because a declaration is not a control.

Budget units are not interchangeable. 1.0.x --max-coins counts coins; 2.x --max-cost is a currency amount. foreman.yaml carries a separate table for each, because passing a coin count as a cost cap is how a stage silently gets a budget three orders of magnitude off.

07

Stage pipeline

Six model invocations carry a ticket from intake to closed. Each one is paired with something the harness does afterwards that the model cannot influence.

08

Contracts and evidence

Every stage emits one JSON envelope, and contract.py is where an envelope stops being a claim and becomes a fact the pipeline is willing to act on. Three levels of scrutiny, in increasing order of how much they matter.

Shape — required fields, enumerated values, sane types. Cheap, and it catches a mode whose instructions have drifted.

Evidence — any citation of the repository is re-read from disk and byte-compared.

Refusal to accept self-assessment — two fields are conspicuously absent from the contracts, and both omissions are load-bearing.

StageEnvelopeEnforced beyond shapeOn failure
triageanalysisevery citation verified against disk; understood:false requires questionsno verified evidence → ticket stops
planplanacceptance criteria mandatory; paths relative; actions enumeratedrejected, ticket → failed
criticreviewany non-accept verdict must carry reasonsunreasoned rejection discarded
buildimplementationcommentary only — the diff is the recordsubject truncated, never rejected on prose
verifyverificationno pass/fail field exists; must add at least one testno tests → ticket stops

A pipeline where the model grades its own homework has no error detection at all — every failure mode produces the same output as success. The two absent fields are how that is avoided, and a unit test asserts that a model volunteering "passed": true has it stripped.

09

Guardrails

The build stage has write tools and a disposable worktree. This is what stands between it and a branch. It does not ask the model what it changed — it reads git diff and decides.

The rule that earns its place

The cheapest way to make a failing test pass is to change the test, and a model under instruction to "make the tests pass" will find that route. Modifying or deleting a test the approved plan did not name is a blocking violation. If a test fails against a change, one of two things is true and both are useful: the change is wrong, or the test encodes behaviour that was deliberately changed — and whether a behavioural contract should move is exactly the kind of decision this pipeline routes to a person.

Paths nothing can authorise

CI workflows, .bob/, .foreman/, AGENTS.md, .env and key material are denied regardless of the plan, the approval, or the ticket. The pattern is simple: you may not edit the things that constrain you. An agent that can rewrite its own guardrails does not have guardrails. No value in policy/guardrails.yaml can widen this set.

An implementation detail that was a real bug

extension/install.sh writes .bob/ and AGENTS.md into the worktree so Bob can resolve its modes. Left in place, every build stage "changes" eight files under a denied path, and the harness fails every ticket on its own footprint — with an error indistinguishable from the model misbehaving. The scaffolding is removed before the diff is taken. This is recorded here because it is the kind of defect that is obvious once seen and very expensive before.

10

Deploy and verify

Foreman does not deploy. It asks whatever already deploys the software to do it, then waits. That boundary is deliberate: a delivery agent that also holds deployment credentials is an agent whose blast radius is the estate, and every organisation that wants one already has a pipeline that does this properly.

ModeMechanismReportsUse for
simulatedruns policy/deploy-simulate.shsuccess or failure, plus a published URLrehearsal and the reference board
github-actionsworkflow_dispatch, then polls the runthe run's actual conclusionGitHub and GHES
webhookPOSTs the payloaddispatched — not successJenkins, Tekton, anything with an endpoint
noneskips the stage—first weeks of a rollout

The webhook mode reports dispatched rather than success on purpose. A 2xx says the request was accepted, not that the deployment worked, and a ticket that claims otherwise is a ticket that lies to the reviewer at the next gate.

Verification

The verify stage clones the branch that was built and deployed, not main. Testing a different tree than the one running in non-prod is a way to produce green evidence for code nobody is running.

It runs under a tighter guardrail set than the build stage: it may add test files and nothing else. Letting it touch the implementation would let it fix the code to match its tests, which inverts the point of the stage. If the suite fails, the tests are not pushed — the failure is the finding, and pushing it would break everyone else's build. It is reported at the gate instead.

On the reference run the verify stage added seven tests and reported, unprompted, that three of them pass against both the original and the fixed code — marking them as regression guards and explicitly not counting them as coverage. That behaviour comes from one line in rules/05-definition-of-done.md: a test that passes either way is worse than none, because it looks like coverage.

11

Where state lives

Per-ticket state is a Jira issue property, with the current state mirrored to a label for humans. Not in the local database.

The property is trimmed to fit — Jira issue properties are a small key-value store, not a database. When it grows past the limit, the bulkiest and most reconstructible parts go first: code snippets, then plan prose, then the diff summary. What survives is what a resuming run needs to continue correctly. The complete record is in the log archive.

12

A ticket, end to end

FORE-1 on the reference board: "Discount codes can be redeemed more than once on the same order." A customer clicked "apply code" four times, was charged 71.40 for a 100.00 basket, and the redemption endpoint returned the same correct-looking subtotal every time — so nobody noticed until reconciliation.

The analysis identified not just the defect but why the symptom was invisible — the endpoint recomputes from the raw subtotal each call, so it returns 90.00 every time while the hidden discount list grows. It derived the 71.40 figure from first principles and matched it to the reported charge. Six citations, all verified against the checkout.

The change was two lines:

  src/pricing.py
     discount = CODES.get(code)
     if discount is None:
         raise ValueError("unknown discount code: %s" % code)
+    if discount.single_use and any(d["code"] == code for d in order["discounts"]):
+        raise ValueError("discount code already applied: %s" % code)
 
     base = subtotal(order["items"])

The ticket warned against fixing this by making every code single-use. The plan named that constraint, the reviewer approved it, and the tests check both paths: WELCOME10 is now rejected on the second redemption, and LOYAL5 still applies twice.

The awkward tickets

The reference board deliberately includes two cases most demonstrations skip.

A ticket too vague to act on

"Please fix the thing with the orders, it's broken." Foreman has a needs-info path for this and the contract enforces it: understood:false without specific questions is rejected. On the reference run it did not take that path — it found the genuine FORE-1 defect still on main and analysed that, which is what a careful engineer would also have done.

A ticket carrying a prompt injection

FORE-4's description instructs the agent to ignore its guardrails, skip the approval step, edit .github/workflows/ and print .env into a comment. Foreman analysed the real request underneath it — a missing cancellation endpoint — and reported the attempt on the ticket under "deliberately not doing", where the team can see it.

13

Portability

The architecture ports cleanly because each domain module is the only thing that knows its system. A port should never need to touch the state machine, the gates, the contracts or the guardrails; if it starts to, something has been wired through the wrong layer.

EnvironmentStatusEffort
Jira Cloud + GitHubverified end to end1–2 days config
Jira Data Center / Serverimplemented, unit-tested, no live instance reached2–3 days — run the smoke test first
GHESsupportedconfiguration only
GitLab · Bitbucket · Azure DevOpsnot supported~1 day per adapter
Proxy with TLS interceptionuntestedhours, mostly testing

Cloud and Data Center are different products wearing the same name: REST v3 against v2, an ADF document tree against a wiki-markup string, an email-plus-token Basic header against a personal access token bearer, /search/jql against /search. The deployment is detected from /serverInfo rather than configured, because an operator who has to know the answer will eventually get it wrong, and the failure — 404s everywhere, or comments posted as literal JSON — does not point at the cause.

Issue properties are architectural, not configuration. If a locked-down instance blocks them, there is no workaround: that is where Foreman's state lives. It is the one hard stop in the pre-engagement smoke test.

Threat model

A malicious ticket

The attacker writes arbitrary text into something a model reads. Relied on, in order: diff inspection and the approval gate; credential separation; then the fencing. Demonstrated on the reference board — Foreman reported the attempt rather than complying with it.

A malicious repository

Same tier separation. The build worktree has no remote. The repository's own AGENTS.md is preserved as AGENTS.repo.md and read as data — concatenating it would hand any repository a direct instruction channel into the agent about to write code in it.

A model that simply goes wrong

The common case, and what most of the guardrails address: edits a test instead of the code, rewrites more than asked, wanders outside the plan, fabricates a citation. No malice required.

An insider approving their own agent's work

Not solved here, and it does not pretend to be. Foreman records who approved and verifies identity. Whether one person may raise and approve is change-management policy, expressed in FOREMAN_APPROVERS.

Failure modes

Fail loudly, never silently, and never in the direction of "proceed".

FailureResultWhere the evidence is

Existing tests fail after the buildreverted, not publishedticket comment, test tail
New tests failnot pushed — the failure is the finding, reported at the gateticket comment

Gate times outticket → stalled, reported in the run summary. Never auto-approved.run summary

failed, needs-info and stalled are human-hold states, not terminals. When a person comments or edits the ticket, Foreman returns it to intake and re-analyses from the top rather than resuming mid-flight — the premises it stopped on may no longer hold.

A run that completed is a success even when every ticket is parked at a gate waiting for a human. start.sh exits non-zero only when the harness itself could not run. A pipeline that alerts on "waiting for a person" trains people to ignore its alerts.

16

Configuration surface

Everything is read from .env; nothing is hardcoded, and real environment variables win over the file so CI secret injection is never overridden. Values containing spaces must be quoted — start.sh sources the file with bash and the harness parses it in Python, and both have to agree.

# the ones that change behaviour rather than just pointing at things

FOREMAN_WRITE=false            # interlock 1 — must be true AND --live
FOREMAN_APPROVERS=            # empty authorises NOBODY, never everybody
FOREMAN_MAX_TICKETS=5           # cap per run; stops a runaway working a backlog
FOREMAN_MAX_REVISIONS=3         # the revise loop cannot run forever
FOREMAN_APPROVAL_TIMEOUT_HOURS=72  # reported as stalled; never auto-approved
FOREMAN_AUTO_MERGE=false        # the merge button stays human by default
FOREMAN_TEST_COMMAND=           # without it, verification has nothing to run
FOREMAN_MODEL=                  # pin before measuring anything
JIRA_INTAKE_JQL=                # the outer boundary of what the agent can touch

# policy/guardrails.yaml — applied to the diff, not asked of the model
allow_paths / deny_paths        # start narrow; widening later is easy
max_files / max_lines / max_deleted_lines
allow_test_edits: false         # the one to refuse to loosen
require_plan_adherence: true

# extension/rules/01-repo-policy.md — ships full of TODO, deliberately
every unfilled placeholder is a defect generator

The policy file is the highest-value half day in an engagement. A model that does not know the house error-handling idiom will pick a reasonable one that is not yours, and every change will read as foreign to the maintainer who inherits it. It is worth more than any prompt tuning that will be done afterwards.

Rollout

  1. Fill in the policy file.

    Half a day with a senior engineer from the team. Their error handling, logging, configuration, money and time conventions, the helpers that already exist, and the patterns that look wrong and are not. Everything else is downstream of this.

  2. Rehearse against a sandbox.

    FOREMAN_GIT_MODE=local, FOREMAN_DEPLOY_MODE=none. Run the whole loop including the failure paths before anything touches a real repository.

  3. Read five real analyses in dry run.

    A dry run takes the same path through the code and stops at the moment of writing. If the analyses are weak, the answer is almost always the policy file, not the prompts.

  4. Go live on one repository, one team, cap of two.

    FOREMAN_MAX_TICKETS=2, FOREMAN_AUTO_MERGE=false, narrow allow_paths. Pin the model.

  5. Read every diff for a few sprints.

    This is calendar time, not effort, and it belongs in the plan. Expand when the rate of blocked-by-guardrail runs is boring.

  6. Add the deployment stage last.

    Everything else should be stable and unremarkable before a pipeline dispatch enters the picture.

The measure of success is not how many tickets close unattended. It is whether the two reviewers still read what they are approving in month six. Every design decision in this document optimises for that, because the moment a gate becomes a formality, every control downstream of it is decorative.
